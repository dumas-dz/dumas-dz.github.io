# DApp 架构与工程边界

## 1. 学习目标

读完后能够画出 DApp 从用户意图到链上确认、索引和通知的链路，明确哪些逻辑必须上链、哪些适合后端，以及故障时如何降级。

## 2. 适用场景

适用于代币工具、NFT、治理、游戏、身份和跨协议产品。单个合约实现见 [Solidity 工程基础](./03-solidity-basics.md)，前端连接见 [钱包、ethers 与 viem](./06-wallet-frontend-ethers-viem.md)。

## 3. 前置知识

- 理解 HTTP API、数据库、队列、缓存和前端状态。
- 理解钱包签名、RPC、receipt、事件和索引器。
- 能描述项目的资产、角色和一致性要求。

## 4. 核心概念

### 4.1 参考链路

```text
用户意图
  -> 前端校验与风险展示
  -> 钱包签名
  -> RPC 广播
  -> EVM 执行并产生 receipt/event
  -> 索引器或后端任务
  -> 查询 API / WebSocket 通知
  -> 前端状态更新与审计记录
```

### 4.2 职责边界

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| 前端 | 展示意图、状态、错误、签名入口 | 保管私钥、决定链上权限 |
| 钱包 | 签名、网络和账户选择 | 替代业务后端或索引 |
| 合约 | 可验证规则、资产状态、事件 | 私密数据、复杂业务查询 |
| RPC | 查询和广播，提供节点视图 | 业务级最终事实 |
| 后端 | 任务编排、通知、风控、缓存 | 代用户持有私钥 |
| 索引器 | 事件查询、排序、聚合 | 未经确认的资金结算 |

### 4.3 一致性与幂等

链上写入可能延迟、替换或回滚，后端任务必须以 txHash、logIndex、blockHash 做幂等键。建议状态：

```text
intent_created -> signed -> broadcast -> mined -> confirmed -> indexed
                                -> replaced / failed / expired
```

前端允许乐观显示，但必须标记“待确认”，并在 receipt 失败时回滚或提示人工处理。不同 RPC 的 `pending` 和 `latest` 视图可能不同。

### 4.4 可观测性

至少记录请求 ID、用户地址、chain ID、合约地址、方法、txHash、gas、receipt 状态、RPC 延迟和索引高度。日志禁止记录私钥、助记词、完整签名材料和敏感授权。监控异常 Gas、失败率、索引落后和管理员操作。

## 5. 最小实践：画出并实现一条写链路

选择一个“登记字符串”的合约，完成：

1. 前端展示目标网络和费用上限。
2. 钱包签名并发送交易，保存 txHash。
3. 后端消费 receipt 和事件，按 `txHash-logIndex` 幂等写入数据库。
4. 索引器落后时前端显示旧数据和高度。
5. 模拟 RPC 超时、拒签、revert 和重组，检查每个状态的恢复动作。

## 6. 生产实践

- 前端配置多 RPC、超时、重试和 chain ID 校验；关键读取可直接查合约。
- 后端使用队列消费事件，设置重试上限、死信队列和人工重放工具。
- 合约、ABI、前端、索引 schema 和 API 版本一起发布，提供兼容性矩阵。
- 高风险操作使用多签、时间锁、限额、暂停和分阶段发布。
- 每次网络切换、授权、提款和管理员操作都进入审计日志。

## 7. 常见坑

- 把中心化数据库当链上事实，用户无法验证余额和交易。
- 让后端托管用户私钥，扩大了被盗和合规风险。
- 只设计 happy path，没有 replaced、failed、expired、reorg 状态。
- 事件数据无幂等键，消费者重试造成重复余额或订单。
- 前端、合约和索引器各自定义金额单位或地址大小写规则。

## 8. 练习

1. 为一次代币转账画出组件时序，标出每一步的信任假设。
2. 设计幂等消费表结构，并测试同一日志重复消费。
3. 列出一个 DApp 在 RPC、索引器和数据库分别故障时的降级策略。
4. 为高风险操作设计权限矩阵和审计事件。
