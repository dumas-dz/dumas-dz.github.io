### 1. RAG 召回不准怎么解决？

**面试场景：** 面试官问你 RAG 召回不准怎么解决。

#### ❌ 常见错误回答

> "换个更好的向量模型"

九成的问题不在于向量模型，而在于**单路检索的短板**。真实项目中，遇到编号、错误码等专有名词，光靠向量检索往往会答非所问。

#### ✅ 标准解法

**混合检索（关键词 + 向量）+ 重排组合拳**

| 层级 | 方法 | 解决的问题 |
|------|------|------------|
| 检索层 | 关键词检索（BM25） | 精确匹配编号、错误码等专有名词 |
| 检索层 | 向量检索 | 语义相似度匹配 |
| 融合层 | 混合检索 | 两路结果合并，互补短板 |
| 重排层 | Rerank 模型 | 对候选结果精排，提升精确率 |

#### 🔑 核心要点

- 向量检索擅长语义匹配，但对精确词条（编号、专有名词）无能为力
- 关键词检索擅长精确匹配，但不懂语义
- **混合检索 + 重排** 是工程上的标准组合拳
- 面试中要展示从底层逻辑到工程落地的完整思路

### 2. 如何真正抑制大模型幻觉？

**面试场景：** 面试大模型岗位时，被问到"RAG 系统如何抑制幻觉"。

#### ❌ 常见错误回答

> "修改 Prompt 就行了"

太浅了。真实线上环境中，抑制幻觉需要一套**从检索、生成到校验的分层防线**。

#### ✅ 标准解法：三层分层防线

| 层级 | 策略 | 具体做法 |
|------|------|----------|
| **检索层** | 提升召回 | 确保相关知识能被检索到，减少信息缺失 |
| **生成层** | 强制引用与拒答 | 要求模型必须基于检索内容回答，无依据时强制拒答 |
| **校验层** | 双重核对 | 生成后再做事实核查，对比回答与原文是否一致 |

#### 🔑 核心要点

- 区分**事实性幻觉**（内容与事实不符）和**忠实性幻觉**（与检索内容不符）
- 不能只靠某一层，需要多层协同防御
- 建立"检索-生成-校验"的完整工程方案

### 3. RAG 里的 TopK 设多少？

**面试场景：** 面试官问你 RAG 里的 Top K 一般设多少？

#### ❌ 常见错误回答

> 脱口而出"5"或者"10"

这道题表面问数字，**实际考的是你对检索中"召回率"和"精确率"核心矛盾的理解**。

#### ✅ 标准解法

| K 值 | 效果 | 问题 |
|------|------|------|
| **太小** | 精确率高 | 容易漏掉关键信息，召回率低 |
| **太大** | 召回率高 | 引入噪声，增加成本和延迟，甚至带偏大模型 |

#### 🔑 满分回答框架

需要结合以下三个因素综合考虑：

1. **切片大小（Chunk Size）**：切片越大，K 可以适当减小；切片越小，K 需要增大
2. **引入重排模型（Rerank）**：先大 K 召回，再用 Rerank 精排，兼顾召回率和精确率
3. **离线评估**：用评测数据集量化不同 K 值的效果，数据驱动决策

> **核心思维：** Top K 不是拍脑袋定的，而是基于召回率与精确率的权衡、切片大小、重排策略以及离线评估综合决定的。

### 4. RAG 怎么处理表格和扫描件？

**面试场景：** 面试被问 RAG 检索全错怎么排查？

#### ❌ 常见错误回答

> "检索没调好"

真实项目中，**RAG 的命门往往在第一步的文档解析**。表格被拍扁、扫描件没文字，检索再准也是白搭。

#### ✅ 标准解法

| 问题类型 | 核心挑战 | 解决方案 |
|----------|----------|----------|
| **表格** | 表格被"拍扁"成无结构文本 | 保留表格结构，转成 Markdown 格式 |
| **扫描件** | 图片中没有可检索文字 | OCR 提取文字 + 多模态视觉模型兜底 |
| **混合文档** | 不同类型文档混杂 | 工程上运用混合策略，按文档类型分流处理 |

#### 🔑 核心要点

- 文档解析是 RAG 的第一步，也是最容易出问题的一步
- 表格不能简单提取纯文本，要保留行列结构（转 Markdown）
- 扫描件需要 OCR + 多模态视觉模型双重保障
- 工程上需要针对不同文档类型设计混合解析策略

### 5. MCP 和 Function Calling 有什么区别？

**面试场景：** 面试官问 MCP 和 Function Calling 的区别。

#### ❌ 常见错误回答

> "MCP 就是替代 Function Calling 的"

**答替代就错了！** 两者不是替代关系。

#### ✅ 标准解法

| 概念 | 职责 | 本质 |
|------|------|------|
| **Function Calling** | 生成意图，把自然语言变成结构化请求 | 模型的意图表达能力 |
| **MCP** | 让调用被标准化执行的协议 | 工具发现与结果返回的标准协议 |

#### 🔑 核心要点

- 两者是**前后配合的上下游关系**，而非替代
- Function Calling 负责"想"——把用户意图转化为可执行的结构化请求
- MCP 负责"做"——标准化工具的发现、调用和结果返回
- 面试关键：理清**模型意图表达**与**标准化执行**的本质区别

### 6. 多 Agent 协作通信怎么设计？

**面试场景：** 面试被问到多 Agent 协作通信怎么设计。

#### ❌ 常见错误回答

> "就是互相发消息"

多 Agent 系统失败往往是因为**交接时上下文断裂**。

#### ✅ 标准解法：三大核心设计

| 设计要点 | 说明 | 解决的问题 |
|----------|------|------------|
| **选对通信拓扑** | 星型、网状、管道等拓扑结构 | 决定 Agent 之间的信息流转路径 |
| **定好消息契约** | 明确消息格式、字段和语义 | 防止 Agent 之间"鸡同鸭讲" |
| **管好共享状态** | 维护全局上下文和中间状态 | 防止交接时上下文断裂 |

#### 🔑 核心要点

- 多 Agent 协作 ≠ 简单的消息收发
- 上下文断裂是多 Agent 系统最常见的失败原因
- 需要像设计微服务通信一样，严肃对待 Agent 间的通信架构
- 向面试官展现真正的工程思维

### 7. 单智能体扛不住，如何上多智能体？

**面试场景：** 面试官问"单智能体扛不住时怎么上多智能体"。

#### ❌ 常见错误回答

> "多开几个 Agent 就行了"

这道题的核心在于考察你对**任务拆解、上下文隔离以及成本兜底**的理解。

#### ✅ 标准解法

**主流编排模式：主管 + 执行者（Orchestrator-Worker）**

| 步骤 | 说明 |
|------|------|
| **任务拆解** | 将复杂任务拆分为可独立执行的子任务，明确任务边界 |
| **上下文隔离** | 每个 Agent 拥有独立的上下文空间，避免互相干扰 |
| **编排协调** | 主管 Agent 负责分发任务、汇总结果 |
| **成本兜底** | 监控 Token 消耗，设置预算上限，防止失控 |

#### ⚠️ 需要避开的坑

- **Token 消耗失控**：多 Agent 会成倍增加 Token 消耗
- **失败传染**：一个 Agent 失败可能级联影响整个系统

### 8. 意图识别怎么设计？

**面试场景：** 面试被问意图识别怎么设计。

#### ❌ 常见错误回答

> "直接丢给大模型"

真实项目中全靠大模型会导致**延迟、成本和稳定性崩溃**。这道题核心考查**工程分层设计**。

#### ✅ 标准解法：三层漏斗架构

| 层级 | 方法 | 处理对象 | 优势 |
|------|------|----------|------|
| **第一层** | 规则引擎 | 简单请求（关键词匹配、正则） | 极快、零成本 |
| **第二层** | 小模型 + 上下文 | 常规意图 | 平衡速度与准确率 |
| **第三层** | 大模型 + 工具调用 | 复杂需求 | 能力最强，兜底保障 |

#### 🔑 核心要点

- 层层过滤，90%+ 的请求在前两层就能解决
- 只有必要时才调用大模型，大幅降低延迟和成本
- 三层架构平衡了**准确率、延迟和成本**
- 这道题考的是工程化思维，而非纯技术能力

### 9. Agent 工具调用失败怎么处理？

**面试场景：** 面试官问你 Agent 调用工具失败了怎么做错误恢复？

#### ❌ 常见错误回答

> "重试一下"

只知道"重试"基本就暴露了你**没做过真正上线的 Agent**。真实生产环境中，接口超时、模型参数填错等问题频发。

#### ✅ 标准解法：先分类，再对症处理

| 错误类型 | 特征 | 处理策略 |
|----------|------|----------|
| **临时性错误** | 接口超时、网络抖动 | 退避重试（Exponential Backoff） |
| **确定性错误** | 参数填错、格式不对 | 让模型自我纠正（Self-Correction） |
| **严重错误** | 系统级故障、数据异常 | 保存状态，交给人处理（Human-in-the-loop） |

#### 🔑 核心要点

- 不能一刀切"重试"，需要**分类兜底**
- 临时性错误重试有效，但确定性错误重试只会重复失败
- 严重错误需要人工介入，不能盲目自动化
- 这种**分类兜底的工程思维**是面试加分项

### 10. 上下文窗口爆了怎么办？

**面试场景：** 大模型面试常考题——"Agent 执行长任务时，上下文窗口爆了怎么办？"

#### ❌ 常见错误回答

> "换一个上下文更大的模型"

如果只回答换大模型，这题就废了。面试官真正想听的是**"上下文管理"**。

#### ✅ 标准解法：四大核心打法

| 策略 | 做法 | 原理 |
|------|------|------|
| **高质量摘要压缩** | 对历史对话做摘要，保留关键信息 | 用摘要替代原始长文本 |
| **引入外部记忆** | 将中间结果存入外部存储（DB/向量库） | 释放上下文空间，按需取回 |
| **按需即时检索** | 只在需要时从外部检索相关信息 | 避免"一股脑全塞进上下文" |
| **子任务拆分隔离** | 将长任务拆分为子任务，各子任务独立上下文 | 避免上下文累积膨胀 |

#### 🔑 核心要点

- 把上下文当成**稀缺资源**精打细算
- 四种策略可以组合使用
- 目标是让 Agent **稳定执行长任务**，而非简单扩容

### 11. 线上 Agent 太烧钱怎么降本？

**面试场景：** 面试被问"Agent 如何控制成本"。

#### ❌ 常见错误回答

> "换一个更便宜的模型"

只回答换便宜模型是不够的。真正的生产级降本需要一套**组合拳**。

#### ✅ 标准解法：从量和价两头算账

| 策略 | 做法 | 降本原理 |
|------|------|----------|
| **模型路由** | 按任务难度分发请求 | 简单任务用小模型，复杂任务才用大模型 |
| **提示词缓存** | 缓存重复的 Prompt 片段 | 避免重复内容反复计费 |
| **上下文瘦身** | 精简冗余 Token | 减少每次请求的 Token 数量 |

#### 🔑 核心要点

- 降本 = 降单价（模型路由） + 降用量（缓存 + 瘦身）
- 需要**从量和价两头算账的工程思维**
- 在企业级应用中有效控制账单

### 12. Tool 和 Skill 的区别？

**面试场景：** 面试官问你 Skill 和 Tool 的区别。

#### ❌ 常见错误回答

> 只背定义

这道题实际在试探你**有没有真正落地过 Agent 分层架构**。

#### ✅ 标准解法

| 概念 | 定位 | 解决的问题 |
|------|------|------------|
| **Tool（工具）** | 让模型能动手的能力 | "能不能做"（执行力） |
| **Skill（技能）** | 让模型知道怎么动手的经验 | "做得对不对"（领域规范） |

#### 🔑 核心要点

- 它们在业务中是**配合关系**，不是替代关系
- Tool 提供**执行力**，Skill 提供**领域规范**
- Tool 是"手"，Skill 是"脑子里的经验"
- 搞懂这套工程认知，才能更好地理解大模型开发

### 13. Agent 技能如何做版本管理？

**面试场景：** 面试被问"Agent 的 Skill 怎么做版本管理"卡壳了。

#### 核心考察点

这道题核心考察你是否把 Skill 当成**线上工程资产治理**，而不是一次性提示词。

#### ✅ 标准解法：两层版本管理

| 层级 | 策略 | 具体做法 |
|------|------|----------|
| **源头层（开发）** | Git 演进 + 语义化版本控制 | 用 Git 管理 Skill 定义，语义化版本号（如 v1.2.0）标记变更 |
| **运行时（线上）** | 版本锁定 + 灰度发布 + 回滚 | 线上锁定特定版本，灰度逐步放量，出问题快速回滚 |

#### 🔑 核心要点

- **拒绝把 Skill 当成一次性提示词**
- Skill 是线上工程资产，需要完整的版本管理生命周期
- 开发时：Git + 语义化版本
- 运行时：版本锁定、灰度发布、快速回滚
- 建立**真正的工程化上线思维**

### 14. Attention 机制的原理？

**面试场景：** 面试被问 Attention 机制。

#### ❌ 常见错误回答

> 张口就背 QKV 公式

这道题考的不是默写，而是你是否**真正理解每一步背后的逻辑**。

#### ✅ 标准解法：三步核心

| 步骤 | 操作 | 大白话解释 |
|------|------|------------|
| **第一步** | Q × Kᵀ | 算相关度——Query 和每个 Key 做点积，衡量有多相关 |
| **第二步** | Softmax | 变权重——将相关度分数归一化为注意力权重 |
| **第三步** | × V | 加权求和——用权重对所有 Value 加权求和，得到最终输出 |

#### 🔑 关键概念

- **Query（查询）**：当前要计算的 token，"我在找什么"
- **Key（键）**：其他 token 的标签，"我有什么"
- **Value（值）**：其他 token 的实际内容，"我的具体信息"
- **除以 √d 的工程意义**：防止点积结果过大导致 Softmax 梯度消失（缩放因子）

### 15. 为什么需要位置编码？

**面试场景：** 面试被问到"为什么 Transformer 要加位置编码"。

#### 核心考点

这其实在考你对 **Attention 机制**的理解。Attention 天生对顺序不敏感，必须额外注入位置信息。

#### ✅ 标准解法：位置编码的演进

| 阶段 | 方法 | 特点 |
|------|------|------|
| **早期** | 正弦绝对位置编码 | 使用固定的正弦/余弦函数生成位置向量 |
| **主流大模型标配** | RoPE 旋转位置编码 | 通过旋转矩阵编码相对位置关系 |

#### 🔑 核心要点

- **Attention 天生对顺序不敏感**——如果不加位置编码，"猫咬狗"和"狗咬猫"对 Attention 来说是一样的
- **相对距离比绝对位置更重要**——RoPE 的核心思想
- **RoPE 如何解决长上下文扩展问题**——这是当前主流大模型的标配方案
- 回答这道题的关键：从 Attention 的无序性出发，讲清楚为什么需要位置编码，再讲 RoPE 的优势

#### 共性面试技巧

1. **千万别背公式/定义**——面试官考的是理解，不是默写
2. **展示工程思维**——分类处理、分层架构、组合拳策略
3. **从"量"和"价"两个维度思考**——成本控制的核心逻辑
4. **把概念当成线上资产治理**——工程化、版本化、可回滚
5. **区分"能做"和"做得对"**——Tool vs Skill 的本质区别
