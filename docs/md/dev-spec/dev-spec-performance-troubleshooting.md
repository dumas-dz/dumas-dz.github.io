# 性能与故障排查

## 1. 学习目标

- 用吞吐、延迟分位数、错误率、饱和度和资源使用描述性能目标。
- 从现象到请求链路再到进程/数据库/中间件逐层缩小瓶颈范围。
- 识别常见 Java、JVM、线程池、数据库、缓存、RPC 和消息问题。
- 在不扩大故障的前提下恢复服务，并保留证据用于复盘。

## 2. 适用场景

适用于接口变慢、吞吐不足、CPU/内存升高、GC 频繁、线程阻塞、数据库慢查询、缓存击穿、消息积压、RPC 超时和容量规划。功能错误优先按日志和业务状态排查，不要把所有失败都当作性能问题。

## 3. 排查原则

1. **先止损，后定位**：先限流、降级、扩容或回滚止住影响，再保留现场。
2. **先测量，后猜测**：先确认时间范围、受影响接口、错误率、P50/P95/P99、QPS 和资源变化。
3. **沿请求链路缩小范围**：客户端/网关 → 应用 → 数据库/缓存/MQ → 外部依赖。
4. **一次验证一个假设**：改变一个变量，记录前后指标，避免同时调多项参数。
5. **区分容量与缺陷**：容量不足需要负载模型和扩展策略；热点代码、锁或死循环需要修复实现。
6. **保留可回滚动作**：参数调整、流量切换和扩容都要记录命令、版本和观察结果。

## 4. 最小实践：建立性能基线

先用可控并发和固定数据集压测，记录：

| 指标 | 作用 | 示例 |
| --- | --- | --- |
| 吞吐 | 单位时间完成请求 | 1200 req/s |
| 延迟 | 用户等待时间 | P95 420 ms、P99 1.2 s |
| 错误 | 超时、拒绝、5xx | 0.2% |
| 饱和度 | 队列、线程、连接、内存 | 连接池 80% |
| 依赖 | DB、Redis、RPC/MQ | DB P99 80 ms、MQ 积压 0 |

压测必须使用代表性数据和网络环境。只测空表单机、只看平均值或只看 CPU 都不能形成基线。

### 4.1 常用证据命令

```bash
# 查看 Java 进程与启动参数
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info

# 查看线程状态与栈
jcmd <pid> Thread.print

# 生成低开销 Java Flight Recorder 记录
jcmd <pid> JFR.start name=incident duration=120s filename=incident.jfr

# 查看数据库执行计划（先使用只读查询）
EXPLAIN ANALYZE SELECT id, status FROM orders WHERE tenant_id = ? ORDER BY created_at DESC LIMIT 50;
```

命令输出需要和请求时间窗口、服务版本、JVM 参数、数据库实例及流量变化一起保存。生产执行 `jcmd`/采样前应确认权限、开销和安全策略。

## 5. 瓶颈定位表

| 现象 | 先看证据 | 常见原因 | 处理方向 |
| --- | --- | --- | --- |
| CPU 高 | 线程栈、JFR、热点方法 | 序列化、正则、JSON、计算热点 | 优化算法/缓存/批量 |
| GC 频繁 | 堆曲线、分配速率、对象年龄 | 大对象、日志拼接、缓存无上限 | 减少分配、限界、调参 |
| 线程阻塞 | `Thread.print`、锁竞争、池队列 | 同步锁、慢下游、池耗尽 | 缩短临界区、隔离池、限流 |
| P99 高 | 依赖耗时、GC、排队 | 慢 SQL、长尾 RPC、重试放大 | 超时、查询优化、隔离 |
| 连接耗尽 | 活跃/等待连接、超时 | 慢事务、泄漏、容量不足 | 事务瘦身、泄漏检测、扩容 |
| MQ 积压 | 生产/消费速率、分区、失败日志 | 消费能力不足、毒消息、重试风暴 | 扩消费者、死信、幂等 |
| 缓存命中低 | 命中率、key 分布、TTL | 热点分散、失效风暴、无界缓存 | key 设计、TTL 抖动、限界 |

## 6. 性能检查表

- [ ] 目标是否写成吞吐、P95/P99、错误率和资源预算，而不是“尽量快”？
- [ ] 压测数据、并发、持续时间和环境是否可复现？
- [ ] 是否测量排队、连接池、线程池和依赖延迟，而不只看 CPU？
- [ ] SQL 是否有索引、执行计划、返回行数和事务时长证据？
- [ ] 超时、重试、熔断、限流和降级是否防止故障放大？
- [ ] JVM 堆、GC、线程、直接内存和容器限制是否匹配？
- [ ] 热点、锁、序列化、日志和大对象是否被剖析确认？
- [ ] 每次调参是否有前后指标、变更记录和回滚方式？
- [ ] 容量余量是否覆盖峰值、故障降级和扩容时间？

## 7. 常见坑

1. **只优化平均值**：用户感知由 P95/P99 和失败请求决定。
2. **盲目加机器**：数据库锁、慢查询或下游限流会随扩容继续放大。
3. **堆越大越好**：大堆会增加 GC 选择和恢复复杂度，也可能掩盖泄漏。
4. **重试无预算**：下游变慢时重试形成风暴，应有指数退避、抖动、熔断和总预算。
5. **事务中调用 RPC**：长事务持锁并放大超时，应把外部副作用移到事务外。
6. **缓存无上限或无 TTL**：内存耗尽后全实例同时回源。
7. **把 profiling 当日常常开**：高开销采样会改变系统行为，应按事件窗口采集。
8. **改参数不记录**：无法知道改善来自调参、流量变化还是偶发波动。

## 8. 总结与关联阅读

性能工作是证据闭环：定义目标、建立基线、复现问题、定位瓶颈、单变量修正、验证收益、准备恢复。先解决最限制吞吐或稳定性的资源，不追逐局部微优化。
