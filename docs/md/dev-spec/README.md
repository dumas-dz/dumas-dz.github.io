# 工程方法论与开发规范

工程规范不是“写文档的格式”，而是让代码、接口、故障和决策可以被团队理解、验证和安全演进的共同语言。本目录把日常开发从需求澄清到上线复盘拆成可执行的方法，既适合个人学习，也可直接作为团队约定的起点。

## 学习目标

- 能用检查表把需求转成可验收、可测试、可回滚的开发任务。
- 能识别设计模式要解决的变化点，而不是为了“使用模式”增加抽象。
- 能建立从单元、集成、契约到端到端的测试组合，并为失败定义清晰断言。
- 能输出可检索、可关联、可脱敏的日志，并把日志与指标、链路追踪配合使用。
- 能用证据定位性能问题，区分容量、算法、锁竞争、GC、I/O 和下游故障。
- 能设计稳定、可演进、错误语义明确的 HTTP/RPC 接口。

## 推荐学习方式

1. 先读[工程规范与交付流程](./dev-spec-engineering-spec.md)，建立需求、实现、评审、测试、发布和复盘的闭环。
2. 用[设计原则与模式](./dev-spec-design-patterns.md)处理一个真实模块，只在存在明确变化点时抽象。
3. 为该模块补齐[测试工程](./dev-spec-testing.md)中的最小测试组合，并验证失败能被测试捕获。
4. 按[日志规范](./dev-spec-logging.md)补充关键路径日志，再用[性能与故障排查](./dev-spec-performance-troubleshooting.md)完成一次证据化排障。
5. 对外暴露功能时，按 [API 设计](./dev-spec-api-design.md)评审资源、错误、幂等、分页和版本兼容。

## 通用交付检查表

- [ ] 需求、边界、非目标、验收标准和错误路径已确认。
- [ ] 设计记录关键取舍，代码与测试能解释为什么这样做。
- [ ] 新增接口、数据、配置、依赖和权限均已评审。
- [ ] 自动化测试覆盖主路径、关键失败路径和兼容性。
- [ ] 日志、指标、告警、超时、重试、降级和回滚已验证。
- [ ] 发布有负责人、灰度策略、观察窗口和恢复动作。
- [ ] 上线后用指标与用户反馈验收，并把问题沉淀为测试或运行手册。

## 常见误区

- 把“代码能运行”当作完成，没有测试、观测、容量和恢复证据。
- 把设计模式名称当作目标，引入无真实变化点的复杂层次。
- 测试只覆盖快乐路径，或者用大量端到端测试替代快速反馈。
- 日志打印很多但无法关联请求、用户、操作和结果，且可能泄露敏感信息。
- 性能优化从猜测开始，不先测吞吐、延迟、资源和依赖瓶颈。
- API 只定义成功返回，不定义错误、幂等、限流、分页和兼容策略。
