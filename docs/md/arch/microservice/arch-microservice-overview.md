# 微服务系统与治理

## 1. 学习目标

学习后应能判断何时拆分服务，设计服务边界和契约，配置发现、限流、熔断、超时、灰度和可观测性，并处理跨服务测试、数据和故障扩散。治理目标是让系统在部分失败时仍可理解、可降级、可恢复。

## 2. 适用场景

微服务适合团队独立发布、资源独立扩展、故障隔离或组织边界明确的系统。它把单体内部模块转换为网络服务，增加了接口、数据、部署和运维成本。

边界尚未稳定、强事务频繁、团队很小、业务数据模型连续变化时，模块化单体通常更高效。拆分理由必须是业务或组织问题，不是技术名词。

## 3. 核心原理

### 3.1 服务边界

服务围绕业务能力组织，拥有自己的数据和变更节奏。每个服务有明确 owner、API、SLO、依赖、配置、部署单元和值班责任。跨服务共享数据库会形成事实耦合，应优先复制只读数据或通过事件同步。

### 3.2 通信与契约

同步 RPC 适合低延迟、需要即时结果的查询/命令；异步事件适合解耦、削峰和最终一致。契约需要版本、兼容策略、错误码、幂等和 deadline。API 网关负责认证、路由、限流、观测和协议转换，但不应承载过多业务规则。

### 3.3 流量与故障治理

超时必须短于上游预算；重试只用于幂等和瞬时错误，并使用退避；熔断在持续失败时快速失败；限流保护服务和依赖；舱壁隔离慢依赖。所有策略需要指标和开关，避免配置神秘地改变用户体验。

### 3.4 配置、发布与可观测

配置分静态版本、动态参数和秘密，支持审计、灰度和回滚。发布采用小批量、金丝雀、蓝绿或滚动，健康检查区分 liveness/readiness。日志、指标、追踪组成排障证据，业务指标要能看到用户影响，不只看 CPU。

## 4. 技术决策与对比

| 决策 | 同步 RPC | 异步事件 | 备注 |
| --- | --- | --- | --- |
| 延迟 | 低延迟、立即结果 | 允许延迟 | 明确 SLA |
| 耦合 | 调用方知道契约 | 发布方少知消费者 | 事件需 schema |
| 一致性 | 请求内结果 | 最终一致 | 补偿和对账 |
| 故障传播 | 超时、重试、熔断 | 积压、重试、死信 | 都要隔离 |
| 调试 | trace 易串联 | 需消息轨迹 | 统一 traceId |

| 拆分方式 | 优点 | 风险 |
| --- | --- | --- |
| 按业务能力 | owner 清晰、变更一致 | 跨域流程复杂 |
| 按团队 | 独立发布、责任清楚 | 可能造成接口碎片 |
| 按性能热点 | 独立扩容 | 热点数据同步复杂 |

## 5. 工程实现

### 5.1 服务契约清单

每个服务维护：

- 入口 API/事件、版本和兼容范围；
- 数据事实源、缓存和投影；
- 依赖的 RPC/MQ/数据库，超时和失败策略；
- SLO、SLI、告警、runbook 和 owner；
- 发布、回滚、迁移和下线步骤。

### 5.2 HTTP 错误与幂等

```http
POST /v1/orders HTTP/1.1
Idempotency-Key: order-20261116-001
Content-Type: application/json

{"sku":"SKU-1001","quantity":1}
```

服务端以 `Idempotency-Key` + 请求摘要保存结果，重复请求返回原结果；参数不同而键相同返回 `409 Conflict`。错误响应包含稳定错误码、可读说明、`traceId` 和可重试性：

```json
{
  "error": "INVENTORY_NOT_ENOUGH",
  "message": "库存不足",
  "traceId": "trace-123",
  "retryable": false
}
```

### 5.3 发布检查

1. 变更类型：API、数据、消息、配置和依赖分别列出兼容策略。
2. 测试：单元、集成、契约、端到端、性能、安全和故障注入。
3. 灰度：按租户/流量/实例发布，观察核心 SLI 和日志。
4. 回滚：代码、配置、数据迁移和消息 schema 都能停止/回退。
5. 复盘：记录变更、指标、问题、行动项和复审日期。

## 6. 生产实践

- 网关和服务使用统一认证、授权、审计、密钥和依赖治理。
- 所有外部调用设置 deadline、重试、熔断、限流和连接池上限。
- 统一 traceId 从 HTTP/RPC/MQ 贯穿日志、数据库和任务；采样不能丢掉错误链路。
- 监控 RED（请求率、错误率、延迟）与 USE（使用率、饱和度、错误），补充业务成功率和依赖错误。
- 服务发现、健康检查、优雅停机、DNS、证书和配置刷新纳入发布演练。
- 数据变更采用兼容字段、双读/双写、影子和对账，禁止一次变更破坏旧消费者。
- 为关键依赖准备降级：默认值、缓存、只读模式、排队和人工兜底。

## 7. 常见坑与排查

1. **微服务数量失控**：每个小改动跨多服务，接口、日志和部署成本超过收益，合并边界并共享平台能力。
2. **同步调用链过深**：超时叠加、重试放大和雪崩，使用事件、批处理、缓存和全链路预算。
3. **共享数据库耦合**：服务改表影响其他服务，限制共享读、版本化视图或事件化数据。
4. **错误被吞或统一 500**：缺少稳定错误码和 traceId，无法区分参数、依赖、超时和内部错误。
5. **重试风暴**：所有层同时重试放大流量，重试只在明确错误上启用并采用退避。
6. **配置漂移**：环境配置不同导致测试通过生产失败，配置版本化、校验和回滚。
7. **健康检查不准**：进程活着但依赖不可用，readiness 要检查关键依赖但保持轻量。
8. **发布无回滚**：数据库/消息 schema 不兼容导致无法回退，使用双向兼容和迁移开关。
9. **日志无上下文**：无法把一次用户请求串起来，统一 traceId、spanId 和业务键。

## 8. 总结与关联阅读

微服务治理把系统行为放在契约、流量、数据、发布和观测中管理。拆分不是目标，可靠交付和清晰责任才是；每一项治理规则都要有测量、开关和故障演练。
