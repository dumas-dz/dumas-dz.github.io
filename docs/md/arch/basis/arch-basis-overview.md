# 架构知识体系

## 1. 学习目标

学习后应能从目标、约束、质量属性和演化路径描述系统架构，选择合适的架构风格，并把关键决策写成可复核的 ADR。重点是做取舍和控制复杂度，而不是画更多框图。

## 2. 适用场景

架构方法用于新系统规划、模块拆分、技术选型、容量扩展、遗留系统改造和故障复盘。它既适用于单体应用，也适用于微服务；架构图规模应匹配沟通对象和决策复杂度。

不适合用“为未来假设预留所有能力”替代真实约束。一个小团队的业务系统可能需要清晰模块边界和可部署单体，而不是全套分布式组件。

## 3. 核心原理

### 3.1 架构视图

- **逻辑视图**：模块、领域对象、职责与依赖方向。
- **进程/运行视图**：服务、进程、线程、队列和并发关系。
- **部署视图**：主机、容器、网络、区域、故障域和资源。
- **数据视图**：事实源、缓存、检索投影、数据流与一致性。
- **演进视图**：版本、迁移、兼容、退役和组织边界。

C4 的 Context、Container、Component、Code 是表达这些视图的常用方法，但不能替代质量属性、决策记录和运行证据。

### 3.2 质量属性

可用性、性能、可扩展性、安全性、可维护性、可测试性、成本和合规互相制约。架构评审必须把属性转为可测量目标，例如“核心查询 P95 < 200ms”“单可用区故障后 5 分钟恢复”，并说明假设、测量和失败模式。

### 3.3 复杂度与边界

模块化按业务能力和变更原因划分边界，依赖方向从外向内。跨边界调用要稳定接口、错误语义和版本策略。能用进程内接口解决的问题，不因“微服务先进”而引入网络、部署和一致性成本。

### 3.4 决策与演化

ADR 记录上下文、候选方案、决策、理由、后果、复审条件和替代方案。架构不是一次性蓝图，需要用指标、故障、团队和业务变化持续修订。技术债应有负责人、风险、触发条件和偿还计划。

## 4. 技术决策与对比

| 风格 | 优点 | 代价 | 适用 |
| --- | --- | --- | --- |
| 模块化单体 | 事务、调试、部署简单 | 独立扩展有限 | 业务边界未稳定 |
| 分层单体 | 依赖清晰、易理解 | 领域逻辑易穿透 | CRUD、管理后台 |
| 微服务 | 独立部署、扩展、组织自治 | 网络、数据、运维复杂 | 边界稳定、团队成熟 |
| 事件驱动 | 解耦、削峰、回放 | 最终一致、排查复杂 | 状态变更和异步流程 |
| 管道/过滤器 | 流程可组合 | 调试和状态治理复杂 | ETL、日志处理 |
| CQRS | 读写模型独立优化 | 双模型同步复杂 | 读写压力/模型差异大 |

## 5. 工程实现

### 5.1 一份可复核的 ADR

```markdown
# ADR-001：订单服务暂时保持模块化单体

## 状态
已接受，2026-11-16 复审

## 背景
订单、支付和履约由 4 人团队负责，业务状态边界仍在变化。

## 决策
使用模块化单体，模块间只通过应用服务接口交互；订单事实放 MySQL，
支付结果异步同步到订单模块。

## 理由
当前不需要独立部署；先保留本地事务和低延迟，减少网络故障面。

## 后果
需要严格维护模块依赖；当支付团队独立或订单发布频率显著增加时重新评估。
```

### 5.2 架构质量检查

1. 目标、假设、数据规模和流量峰值是否写清楚？
2. 每个跨进程调用是否有超时、重试、幂等、降级和观测？
3. 数据事实源、缓存、索引和消息的写入/删除是否有一致性方案？
4. 部署是否跨故障域，发布、回滚和恢复是否有演练？
5. 安全边界是否覆盖认证、授权、审计、密钥和依赖漏洞？
6. 模块是否能独立测试，关键接口是否有契约测试？

### 5.3 演进策略

为迁移设置并行运行、影子流量、双写/双读、校验和回滚开关。新旧路径的兼容窗口要有限，旧路径退役时有负责人和日期。不要在一次发布中同时替换数据模型、协议和部署拓扑。

## 6. 生产实践

- 架构图与真实部署同步，标注 owner、数据流、协议、SLI 和故障域。
- 以用户旅程和故障场景评审，而不是只审技术名词。
- 统一时间、日志、追踪、错误码、配置、密钥和版本管理等平台能力。
- 关键架构变更采用小步验证：压测、影子、灰度、回滚、复盘。
- 预算成本、团队能力和认知负担，避免组件数量超过可运维范围。
- 对外部依赖写明 SLA、配额、超时、责任边界和退出方案。

## 7. 常见坑与排查

1. **先选技术后找问题**：没有质量和数据指标的“微服务、分片、服务网格”通常增加复杂度。
2. **架构图只画正常流**：缺少重试、重复、超时、降级、数据修复和人工介入路径。
3. **模块边界渗漏**：跨层读表、共享实体和循环依赖使系统难测试，使用依赖检查和接口评审。
4. **质量属性不可测**：以“高可用、高性能”为目标无法验证，需要 SLO、SLI 和预算。
5. **忽略组织边界**：服务边界必须考虑团队所有权、发布频率和值班责任。
6. **一次性大重构**：没有并行路径、校验和回滚，迁移风险不可控。
7. **只记录结论不记录理由**：后续无法判断约束是否变化，ADR 必须保存背景和复审条件。

## 8. 总结与关联阅读

架构的价值在于在约束下做出可解释、可演进的取舍。质量属性、边界和证据优先于术语；每次决策都要能被运行指标和故障结果检验。
