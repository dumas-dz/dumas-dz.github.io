# MongoDB 详解

## 1. 学习目标

学习后应能根据访问模式设计文档结构，使用索引和聚合管道优化查询，理解副本集、读写关注和多文档事务，并规划从单集合到分片的演进。示例面向 MongoDB 6.0+。

## 2. 适用场景

MongoDB 适合字段频繁演进、读写以文档为单位、需要水平扩展和灵活聚合的业务，例如商品资料、行为事件、配置和内容管理。它能减少对象映射阻抗，但不意味着“Schema Free”：字段含义、约束和索引仍需在应用中治理。

数据关系极其复杂、跨文档强约束很多或以多表复杂关联为核心时，关系数据库通常更简单。MongoDB 事务支持扩展到多文档，但事务范围越大，成本和锁冲突越高。

## 3. 核心原理

### 3.1 文档模型

文档以 BSON 保存，支持嵌套对象和数组。设计原则是“按访问一起读写的字段嵌入，跨文档复用和一对多规模不确定的实体引用”。文档有大小限制，超大数组应拆分，避免每次更新整个数组。

### 3.2 索引和查询

单字段、复合、唯一、部分、TTL 和多键索引覆盖常见访问。复合索引同样需要匹配等值、范围和排序顺序。数组字段会产生多键索引，嵌套字段使用点号访问；查询必须匹配数组语义和字段类型。

聚合管道可完成过滤、分组、连接、排序和投影。`$lookup` 能关联集合，但生产中要结合索引和结果量限制，不要把 MongoDB 当成无代价关系查询引擎。

### 3.3 复制、读写关注和事务

副本集由主节点和从节点组成，写入默认多数确认可提高持久性；读关注可选择本地、多数或快照。写关注越高越安全，但延迟越大。多文档事务提供原子性，适合跨集合保持状态一致，不能替代合理的数据模型。

### 3.4 分片

分片键决定数据分布和查询路由。高基数、写入均匀且能覆盖常用查询的字段更适合；低基数分片键会造成热点。分片后跨片排序、聚合、唯一约束和迁移都需要额外预算。数据量、索引和连接压力尚未接近单副本集极限时，不急于分片。

## 4. 技术决策与对比

| 决策 | 嵌入文档 | 引用文档 | 建议 |
| --- | --- | --- | --- |
| 读取模式 | 总是一起读取 | 可独立变化/查询 | 以高频访问路径为准 |
| 更新模式 | 局部少量更新 | 大数组频繁追加 | 大数组拆集合 |
| 数据关系 | 一对少 | 一对多且无上限 | 引用 + 索引 |
| 一致性 | 单文档原子 | 跨实体强一致 | 事务或重构边界 |
| 扩展 | 单集合热点低 | 查询键均匀 | 分片键先压测 |

## 5. 工程实现

### 5.1 建模示例

```json
{
  "_id": "order-20261116-001",
  "userId": "user-1001",
  "status": "PAID",
  "items": [
    {"sku": "SKU-1001", "quantity": 2, "price": 39.9}
  ],
  "amount": 79.8,
  "createdAt": "2026-11-16T10:00:00Z",
  "updatedAt": "2026-11-16T10:00:02Z"
}
```

创建查询索引：

```javascript
db.orders.createIndex(
  { userId: 1, createdAt: -1 },
  { name: "idx_orders_user_created" }
);
db.orders.createIndex(
  { status: 1, updatedAt: 1 },
  { partialFilterExpression: { status: "PENDING" } }
);
```

### 5.2 条件状态更新

```javascript
db.orders.updateOne(
  {
    _id: "order-20261116-001",
    status: "PENDING"
  },
  {
    $set: {
      status: "PAID",
      updatedAt: "2026-11-16T10:00:02Z"
    },
    $inc: { version: 1 }
  }
);
```

应用要检查 `matchedCount` 和 `modifiedCount`，避免把旧状态覆盖成新状态。

### 5.3 聚合查询

```javascript
db.orders.aggregate([
  { $match: { status: "PAID", createdAt: { $gte: ISODate("2026-11-01T00:00:00Z") } } },
  { $group: { _id: "$userId", amount: { $sum: "$amount" }, count: { $sum: 1 } } },
  { $sort: { amount: -1 } },
  { $limit: 100 }
]);
```

## 6. 生产实践

- 在应用层定义字段类型、长度和状态枚举，使用 schema validation 作为必要约束。
- 查询、更新和聚合必须能对应索引；对不确定查询使用 `explain("executionStats")` 验证。
- 配置合适的 `w`/`j`、读关注和超时，明确强一致与延迟之间的选择。
- 监控连接数、慢查询、复制延迟、锁等待、磁盘 IO、文档大小和索引大小。
- 大批量导入使用 `insertMany` 小批次和有序/无序写入选择，生产前压测写关注。
- 备份和时间点恢复依赖 oplog/日志，定期演练恢复到指定时间。
- 用户输入不能直接拼接 `$where`、JavaScript 或操作符，统一校验字段和值。

## 7. 常见坑与排查

1. **索引与字段类型不匹配**：字符串 `"1001"` 不等于数字 `1001`，会导致全集合扫描。
2. **数组查询语义误解**：多键索引与 `$elemMatch` 的行为不同，需要显式表达数组元素条件。
3. **文档过大**：不断追加数组或日志字段会导致写放大和迁移困难。
4. **`$lookup` 过慢**：右集合缺少关联索引，或返回结果过大。
5. **事务范围过大**：跨集合事务持有资源久、失败重试成本高，应缩小事务边界。
6. **分片键热点**：以时间递增字段作为主分片键可能集中写入，需要评估桶、哈希或复合键。
7. **读到旧数据**：从节点读取可能滞后，写后读使用主节点或多数读关注。
8. **复制延迟被忽略**：长时间运行的索引构建、批量导入和节点故障都可能影响延迟。

## 8. 总结与关联阅读

MongoDB 的文档模型能带来开发效率，但生产性能仍依赖访问模式、索引和一致性的明确设计。选择嵌入还是引用，先从读写路径和边界条件出发。
