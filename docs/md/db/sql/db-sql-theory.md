# 数据库原理

## 1. 学习目标

读完本篇后，应当能够回答三个工程问题：数据为什么能保证一致，查询为什么快或慢，以及一种业务模型应该选择关系库、文档库还是检索引擎。重点不是背诵定义，而是把原理转化为表结构、索引、事务边界和执行计划。

## 2. 适用场景

关系数据库适合实体关系清晰、约束严格、以事务写入和精确查询为主的系统，例如订单、账户、库存和权限。它不天然擅长超大规模日志检索、无固定 Schema 的探索式数据，也不应在单表无节制堆叠所有业务字段。

当读写规模超过单机能力时，优先通过索引、缓存、读写分离和合理分片解决；不要在没有性能数据前直接引入分布式数据库。强一致、复杂关联和可维护性通常是选择关系库的核心理由。

## 3. 核心原理

### 3.1 数据模型与约束

关系模型用行和列表达实体，用主键、唯一约束、外键和检查约束保证数据合法。范式减少冗余，反范式减少关联，但反范式必须明确数据所有者和同步策略。金额使用 `DECIMAL`，时间统一时区，枚举要预留演进空间。

### 3.2 ACID 与隔离级别

- **Atomicity**：事务内操作全部成功或全部回滚。
- **Consistency**：约束、触发器和业务规则共同把数据库从一个合法状态转到另一个合法状态。
- **Isolation**：并发事务互不干扰的程度。
- **Durability**：提交成功后，已确认数据不应因进程崩溃丢失。

常见隔离级别从低到高为 Read Uncommitted、Read Committed、Repeatable Read、Serializable。级别越高，一致性越强，锁冲突和吞吐损失通常越大。不要把“隔离级别”直接等同于“没有并发问题”，还要结合具体数据库的实现。

### 3.3 MVCC 与锁

MVCC 通过版本链让读操作尽量不阻塞写操作。快照读读取事务开始时的可见版本，当前读读取最新已提交版本并加锁。写写冲突、唯一键检查和范围更新仍需要锁。热点账户、库存扣减等场景应缩短事务、固定加锁顺序并使用条件更新。

### 3.4 索引与执行计划

索引把随机查找转换为更少的页读取。B+ 树适合等值、范围和有序扫描；哈希索引只适合等值；全文和向量索引解决不同检索问题。联合索引遵循最左前缀，并尽量让选择性高的列在前；范围条件之后的列通常难以继续用于定位。

优化器基于统计信息、代价模型和索引可用性选择执行计划。`EXPLAIN` 只能说明计划，不能替代业务数据分布分析。真正调优的顺序是：确认慢 SQL → 观察扫描行数与回表 → 修正访问路径 → 调整 SQL 或数据模型 → 最后才考虑改参数。

## 4. 技术决策与对比

| 决策 | 选择条件 | 主要代价 |
| --- | --- | --- |
| 规范化 vs 反范式 | 一致性优先时规范化，高频读且数据稳定时适度反范式 | 范式关联多；反范式存在同步和占空 |
| 聚簇索引 vs 二级索引 | 主键访问快、范围有序；二级索引覆盖更多查询 | 二级索引可能回表，维护成本更高 |
| 乐观锁 vs 悲观锁 | 冲突低、重试成本低选乐观锁；热点写选悲观锁 | 乐观锁空重试，悲观锁可能阻塞 |
| 单库 vs 分片 | 单库容量和连接可承受时不拆分 | 分片牺牲跨分片事务和复杂查询 |
| 同步 vs 异步复制 | 要求提交后强一致选同步 | 同步增加延迟，异步可能丢数据 |

## 5. 工程实现

### 5.1 建模清单

1. 为每个核心实体定义不可变主键，避免使用会变化的业务字段。
2. 金额、数量使用精确类型；时间和状态字段明确默认值与语义。
3. 唯一业务编号必须有数据库唯一索引兜底，不能只靠应用校验。
4. 大字段拆到扩展表，高频查询字段和历史归档分开。
5. 表结构变更使用可回滚迁移脚本，并在生产前用近似数据量验证执行计划。

### 5.2 可执行的事务示例

```sql
CREATE TABLE account_balance (
  account_id BIGINT PRIMARY KEY,
  balance DECIMAL(18, 2) NOT NULL CHECK (balance >= 0),
  version BIGINT NOT NULL DEFAULT 0
);

INSERT INTO account_balance (account_id, balance)
VALUES (1001, 100.00);

START TRANSACTION;
UPDATE account_balance
SET balance = balance - 10.00, version = version + 1
WHERE account_id = 1001 AND balance >= 10.00;
COMMIT;
```

应用需要检查受影响行数；返回 `0` 行不能被当成成功。对于复杂状态流转，使用状态条件更新，避免“读取旧值再覆盖”。

### 5.3 建立性能基线

保留典型 SQL、数据量、P95 延迟、扫描行数和连接池指标。基线至少覆盖日常流量、峰值流量和批处理窗口，调优前后用同一数据集和并发模型比较。

## 6. 生产实践

- 统计信息要定期更新，批量导入后主动刷新统计信息。
- 长事务会阻塞清理、放大锁冲突并导致复制延迟，应设置超时和监控。
- 备份不等于可恢复，必须定期做全量、增量和恢复演练。
- 为慢查询、死锁、连接数、复制延迟、磁盘水位和主从切换建立告警。
- 高可用切换要区分数据恢复点（RPO）和恢复时间（RTO），由业务等级决定复制方式。
- 多租户优先共享库共享表并用租户索引；只有合规或隔离要求明确时才拆库。

## 7. 常见坑与排查

1. **索引失效**：对索引列做函数、隐式类型转换或前置模糊匹配时，可能无法定位。用 `EXPLAIN` 对比改写前后扫描行数。
2. **回表过多**：二级索引选中大量行后再访问聚簇索引。优先覆盖索引或减少返回列。
3. **事务过长**：RPC 调用、文件上传、人工处理不应放在数据库事务内。
4. **唯一冲突重试不明确**：并发写入违反唯一约束时，应用必须明确是幂等成功还是冲突失败。
5. **分页越深越慢**：深度 `OFFSET` 会扫描并丢弃大量数据，改用游标分页。
6. **把数据库当队列**：不断轮询状态表会放大扫描和锁竞争，可靠事件量大时使用消息队列。
7. **错误地以 CPU 作为唯一瓶颈**：大量单行读、锁等待和磁盘抖动也可能造成延迟。

面试追问常见落点是：快照读和当前读的区别、为什么唯一索引能防重、一个慢查询如何从发现到关闭，以及主从延迟对“写后读”的影响。

## 8. 总结与关联阅读

数据库性能来自正确的数据模型、访问路径和事务边界，而不是单一参数。先保证约束和可恢复性，再依据测量结果优化吞吐与延迟。
