## 项目背景

企业内部已经存在 Dify 私有化平台，包含 Agent、Workflow 和 ChatFlow 等编排能力，但业务系统需要更稳定的 API 形态、统一鉴权、流式响应和工具调用入口。直接把平台接口暴露给前端或业务服务，会带来协议差异、错误处理不一致、消息丢失和维护边界不清等问题。

项目目标是在企业侧建立一层智能服务平台集成能力，把 Dify 的编排能力封装为标准、可复用的服务接口，并通过 MCP 形式向其他系统提供工具调用能力。

## 职责范围

我作为核心开发，负责：

- 对接 Dify 私有化企业平台的 Agent、Workflow、ChatFlow 对话 API。
- 设计基于 SSE 的流式响应处理，优化实时对话体验。
- 实现指数退避重试与异步消息持久化，增强接口可靠性。
- 设计并实现 MCP 标准调用 API。
- 基于规则库构建 LLM 客户类型自动匹配工作流。
- 参与 Java 服务与 AI 平台之间的接口协议、错误码和异步任务组织。

## 技术方案

### 平台适配层

通过统一适配层封装 Dify 的不同能力，向上提供稳定的业务接口：

```text
业务系统
  -> 统一 API / 鉴权 / 参数校验
  -> Dify 适配层
  -> Agent / Workflow / ChatFlow
  -> SSE 流式结果
  -> 消息持久化与状态回传
```

这样可以让业务系统不直接依赖 Dify 的内部接口细节，后续更换模型、编排节点或平台版本时，只需要调整适配层。

### SSE 流式响应

基于 SSE 将模型输出逐步推送给调用方，避免长任务只能等待一次性结果。实现时关注：

- 事件边界与消息格式统一。
- 客户端断线和服务端超时处理。
- 失败重试后的消息去重和状态恢复。
- 流式输出过程中如何记录审计和业务状态。

### MCP 工具服务

将规则库和客户类型匹配能力封装为 MCP 标准调用 API。规则库负责稳定约束，LLM 负责理解和泛化，两者结合可以完成客户名称自动分类，同时保留人工可维护的规则入口。

### 关键技术栈

`Spring Boot 3`、`Spring WebFlux`、`WebClient`、`SSE`、`MCP Protocol`、`Dify`。

## 项目成果

- 完成 Dify 私有化平台 Agent / Workflow / ChatFlow 全功能对话 API 对接。
- 通过 SSE 提供实时流式对话响应。
- 通过指数退避重试与异步消息持久化，降低瞬时失败对用户交互和业务处理的影响。
- 设计 MCP 标准调用 API，为其他系统提供统一工具接入方式。
- 将规则库与 LLM 结合，支持客户类型自动匹配工作流。

## 反思与改进

- **集成层要有稳定的协议边界**：平台能力会变化，业务系统不应直接绑定某一版 Dify 的请求和响应细节。
- **流式接口不只是推送文本**：断线、超时、重试、消息顺序和持久化，都属于生产级 SSE 的一部分。
- **MCP 适合工具化，不适合掩盖业务语义**：工具参数、权限、幂等和错误语义需要在设计阶段明确。
- **规则与模型需要分工**：规则提供可控性，LLM 提供泛化能力，最终应通过评测决定各自边界。
