## 项目背景

传统 Java 客服平台主要依靠人工检索知识、判断咨询意图和创建工单。随着咨询类型增多，单纯增加人工规则会让系统出现三类问题：

- 用户问题表达多样，规则无法稳定覆盖意图。
- 历史工单和知识内容分散，检索效率和答复一致性不足。
- 即使完成问答，后续工单创建、分配和 OA 处理仍依赖人工衔接。

项目目标是在不推翻既有 Java 业务系统的基础上，引入 Agent 能力，让咨询从“问答”进入“识别、检索、补充信息、创建工单、下游处理”的业务闭环。

## 职责范围

我作为核心开发，主要负责：

- 设计 Python Agent 中台与既有 Java 客服平台的集成边界。
- 基于 LangGraph 设计 Router + 垂直 Agent 架构，完成意图识别和多业务域协作。
- 构建 RAG 检索增强链路，将历史工单向量化并存储到 Milvus。
- 设计短期上下文与长期用户画像组成的分层记忆系统。
- 基于槽位填充提取关键信息，对接 Java 工单 API，实现工单创建和下游分配。
- 参与流式响应、异步处理、消息持久化和异常恢复设计。

## 技术方案

### 总体架构

```text
用户输入
  -> 意图路由 / Router
  -> 垂直业务 Agent
  -> RAG 检索 + 记忆读取
  -> 槽位填充与业务校验
  -> 工单 API / OA WM
  -> 流式答复与处理结果回传
```

### Router 与垂直 Agent

采用 Router 先判断咨询所属业务域，再由对应垂直 Agent 处理具体任务。这样可以把通用对话能力和业务规则分开：

- Router 负责意图分流、上下文判断和异常兜底。
- 垂直 Agent 负责知识检索、字段提取、工具调用和业务答复。
- Agent 之间通过明确的状态和消息结构协作，避免把所有规则塞进一个超长 Prompt。

### RAG 检索与分层记忆

- 使用 Milvus 对历史工单进行向量化存储，支持语义召回。
- 短期记忆放在 Redis，保存当前会话中的用户输入、槽位和处理状态。
- 长期记忆沉淀用户画像与跨会话偏好，用于个性化答复。
- 检索结果进入回答前，需要结合业务上下文进行筛选、拼接和引用组织，避免直接把低相关片段交给模型。

### 工具调用与工单闭环

槽位填充从自然语言中提取客户、问题类型和处理所需字段。字段完整后调用 Java 工单 API 创建工单并进行下游分配，再对接 OA 办公软件 WM，使咨询结果进入后续办公处理流程。

### 关键技术栈

`Python`、`FastAPI`、`LangGraph`、`Milvus`、`Redis`、`MySQL`、`RabbitMQ`。

## 项目成果

- 将传统客服平台扩展为可编排的 Agent 智能中台，支持多业务域意图识别与协作。
- 基于历史工单形成语义检索能力，为智能答复提供可复用的企业知识基础。
- 通过短期上下文和长期用户画像支持跨会话个性化应答。
- 通过槽位填充、工单 API 与 OA WM 的衔接，形成咨询工单创建、分配和处理的闭环。
- 在实时交互方面，结合流式响应、指数退避重试和异步消息持久化，提升对话连续性和处理可靠性。

## 反思与改进

- **Agent 不是越多越好**：先按业务边界拆分 Agent，再根据调用频率和失败原因优化路由，避免过早增加协作复杂度。
- **RAG 的难点在数据和评测**：向量库只是基础设施，历史工单的清洗、标签、召回质量和引用可解释性决定实际效果。
- **状态必须显式管理**：短期记忆、长期记忆、槽位和工单状态应有清晰生命周期，否则跨会话和异常恢复会变得难以排查。
- **业务闭环优先于聊天体验**：问答只是入口，能否稳定完成工单创建和下游分配，才是衡量企业客服 Agent 的核心标准。
